# fft — go-fft

[![Docs](https://img.shields.io/badge/docs-hugo%20%2B%20relearn-059669)](https://go-fft.github.io/docs/)
[![Playground](https://img.shields.io/badge/playground-try%20it%20in%20your%20browser-059669)](https://go-fft.github.io/playground/)
[![License](https://img.shields.io/badge/license-BSD--3--Clause-blue)](LICENSE)
[![Go](https://img.shields.io/badge/go-1.27.1%2B-00ADD8)](https://go.dev/dl/)
[![Status](https://img.shields.io/badge/status-phase%206-1a7f37)](docs/plan-fft.md)

**A pure-Go (no cgo) FFT library** — the `numpy.fft` / `scipy.fft` equivalent for
Go. It computes the discrete Fourier transform of complex and real signals of
**any length**, with no dependency on the native FFTW3 C library.

**Try it without installing anything:** the [playground](https://go-fft.github.io/playground/)
runs go-fft compiled to WebAssembly in your browser.

Ruby has no cgo-free FFT (every option wraps FFTW3); `gonum/dsp/fourier` is pure
Go but its optimized assembly is amd64-only. This module is a portable Go core
that runs on the six 64-bit Go targets (amd64, arm64, riscv64, loong64,
ppc64le, s390x), with AVX2 and AVX-512 kernels on amd64 and NEON kernels on
arm64, generated by [go-asmgen](https://github.com/go-asmgen) and bit-identical
to the Go code of their arithmetic (fused multiply-adds by default on amd64 with
FMA3, see below).

> **Use v0.26.3 or later.** v0.25.0 to v0.26.2 return wrong N-D results,
> silently, on Intel CPUs with AVX-512 when an axis other than the last has a
> length 9·p ([v0.26.3 release notes](https://github.com/go-fft/fft/releases/tag/v0.26.3)).

> Status: released as v0.28.x (Go 1.27.1 or later). Complex and real transforms
> of any length (`FFT`/`IFFT`, `RFFT`/`IRFFT`, `HFFT`/`IHFFT`), the
> multi-dimensional transforms (`FFT2`/`IFFT2`, `FFTN`/`IFFTN`,
> `RFFT2`/`IRFFT2`, `RFFTN`/`IRFFTN`), numpy's `n`, `norm` and `axes` arguments
> (`...With(Options)`), fused multiply-add plans by default on amd64
> (`Options.FMA`, `NoFMA`, `Exact`), `FFTShift`, `NextFastLen`, the DCT and DST of types
> I–IV, all of these in single precision too (`FFT32`, `FFTN32`, `RFFT2_32`,
> `FFT32With`, `DCT32`, `Plan32`, …), reusable and
> allocation-free plans (`Plan`, `RealPlan`, `PlanN`, `RealPlan2`, `DCTPlan`,
> `DSTPlan`), and the windowing and spectral helpers (windows,
> `FFTFreq`/`RFFTFreq`, `PSD`, `Spectrogram`). The transform is also exposed to Ruby through the
> [go-embedded-ruby](https://github.com/go-embedded-ruby/ruby) `FFT` module.
> See **[docs/plan-fft.md](docs/plan-fft.md)** for the phased roadmap.

## API

```go
import "github.com/go-fft/fft"

X := fft.FFT(x)          // forward DFT of []complex128, any length
y := fft.IFFT(X)         // inverse DFT, normalized by N (IFFT(FFT(x)) ≈ x)
S := fft.FFTReal(r)      // forward DFT of a []float64 signal (full spectrum; real FFT + mirror at even lengths, FFTRealWith Exact keeps promote-then-FFT)

R := fft.RFFT(r)         // real-input DFT, non-redundant N/2+1 bins (numpy.fft.rfft)
z := fft.IRFFT(R, len(r)) // back to []float64 (numpy.fft.irfft)

// Multi-dimensional, on flat row-major (C-order) data plus an explicit shape:
F2 := fft.FFT2(data, [2]int{rows, cols})   // 2-D DFT (numpy.fft.fft2)
d2 := fft.IFFT2(F2, [2]int{rows, cols})    // inverse 2-D DFT (numpy.fft.ifft2)
FN := fft.FFTN(data, shape)                // N-D DFT (numpy.fft.fftn)
dN := fft.IFFTN(FN, shape)                 // inverse N-D DFT (numpy.fft.ifftn)

// Real image-style 2-D transforms (last axis keeps cols/2+1 bins per row):
RG := fft.RFFT2(img, [2]int{rows, cols})   // numpy.fft.rfft2
zG := fft.IRFFT2(RG, [2]int{rows, cols})   // numpy.fft.irfft2

// Windowing and spectral helpers:
w  := fft.Hann(n)             // also Hamming, Blackman, BlackmanHarris, Bartlett
f  := fft.FFTFreq(n, d)       // bin frequencies (numpy.fft.fftfreq)
rf := fft.RFFTFreq(n, d)      // real-FFT bin frequencies (numpy.fft.rfftfreq)
p  := fft.PSD(sig, d)         // one-sided power spectral density (periodogram)
S  := fft.Spectrogram(sig, segment, overlap, fft.Hann(segment), d) // PSD frames

// Reusable plans — precompute the twiddle tables once, amortize across calls
// (no per-call sin/cos). The convenience FFT/RFFT functions above use an
// internal per-length plan cache, so they get this for free too.
p   := fft.NewPlan(n)          // complex transform plan of length n
p.FFT(dst, src)               // dst and src are []complex128 of length n (may alias)
p.IFFT(dst, src)              // normalized inverse
rp  := fft.NewRealPlan(n)      // real-input transform plan
rp.RFFT(dst, src)             // src []float64 (len n), dst []complex128 (len n/2+1)
rp.FFTReal(full, src)         // the full spectrum, full []complex128 (len n), no allocation
rp.IRFFT(out, spec)           // out []float64 (len n), spec the half spectrum

// N-D and real 2-D plans: write into your slice, allocate nothing in steady
// state. FFTN/FFT2/RFFT2 return a new slice each call; on a many-core host
// that allocation, not the FFT, dominates a small repeated transform.
pn  := fft.NewPlanN(rows, cols)      // any rank: NewPlanN(d0, d1, d2, ...)
pn.FFT(dst, src)                     // row-major, len = product of the shape (may alias)
pn.IFFT(dst, src)                    // normalized inverse (matches IFFTN)
r2  := fft.NewRealPlan2(rows, cols)  // real 2-D plan (matches RFFT2/IRFFT2)
r2.RFFT(spec, img)                   // spec len r2.SpectrumLen() = rows*(cols/2+1)
r2.IRFFT(img, spec)                  // normalized inverse
```

The multi-dimensional transforms are separable: the 1-D FFT is applied along
each axis in turn. The forward transforms are unnormalized; the inverses divide
by the product of the transformed axis lengths. The shape must be positive and
its product must equal `len(data)`, else the call panics (numpy semantics). A
length too large to allocate at all (more than `math.MaxInt/16` elements for a
complex128 plan) panics with `fft: <function>: length N is too large`; smaller
lengths allocate in proportion to themselves, so bound a length that comes from
untrusted input (see [SECURITY.md](SECURITY.md)).

Empty input returns an empty slice; length 1 returns a copy. `RFFT` keeps only
the lower `N/2+1` bins because a real signal's spectrum is conjugate-symmetric
(`X[N-k] = conj(X[k])`); `IRFFT` takes the target length `n` explicitly.

### numpy's optional arguments: `n`, `norm`, `axes`

Every transform has a `...With` variant taking an `fft.Options`, whose fields
are numpy's keyword arguments and whose zero value is numpy's defaults — so
`FFTWith(x, fft.Options{})` is `FFT(x)` and a call names only what it changes.
The plain functions keep their signatures. A field that does not apply (`N` on
an N-D transform, `Axes` on a 1-D one) panics rather than being ignored.

```go
o := fft.Options{
	N:    1024,           // numpy n: truncate or zero-pad the input (1-D only)
	Norm: fft.NormOrtho,  // numpy norm: NormBackward (zero value), NormOrtho, NormForward
	Axes: nil,            // numpy axes: nil = all; negative counts from the end (N-D only)
}

X := fft.FFTWith(x, fft.Options{N: 1024, Norm: fft.NormOrtho}) // numpy.fft.fft(x, n, norm=)
y := fft.IFFTWith(X, fft.Options{Norm: fft.NormOrtho})        // numpy.fft.ifft
R := fft.RFFTWith(r, fft.Options{N: 1024})                     // numpy.fft.rfft(r, n)
z := fft.IRFFTWith(R, fft.Options{})                           // numpy.fft.irfft: N=0 → 2*(len(R)-1)

// Hermitian-symmetric input (numpy.fft.hfft / ihfft), any Norm:
h := fft.HFFT(half, n)        // real spectrum of the signal whose first half is `half`
g := fft.IHFFT(h)             // back to the half signal; HFFTWith/IHFFTWith take Options

// N-D, with axes and norm (numpy.fft.fftn/ifftn/fft2/ifft2(axes=, norm=)):
F := fft.FFTNWith(data, shape, fft.Options{Axes: []int{0, 2}, Norm: fft.NormForward})
d := fft.IFFTNWith(F, shape, fft.Options{Axes: []int{0, 2}, Norm: fft.NormForward})
F2 := fft.FFT2With(img, [2]int{rows, cols}, fft.Options{Norm: fft.NormOrtho})

// Batched 1-D transforms: many signals of one length, one plan — numpy's
// fft(x, axis=-1) on a rows×n matrix. Rows run across goroutines when large.
B := fft.FFTNWith(signals, []int{rows, n}, fft.Options{Axes: []int{-1}})
RB := fft.RFFTNWith(realSignals, []int{rows, n}, fft.Options{Axes: []int{-1}})

// Real N-D (numpy.fft.rfftn/irfftn): the real transform runs along the LAST
// axis listed (the last axis by default), which keeps n/2+1 bins.
S := fft.RFFTN(vol, []int{d0, d1, d2})          // shape d0×d1×(d2/2+1)
v := fft.IRFFTN(S, []int{d0, d1, d2})           // the REAL output's shape
S2 := fft.RFFTNWith(vol, shape, fft.Options{Axes: []int{2, 0}, Norm: fft.NormOrtho})
v2 := fft.IRFFTNWith(S2, shape, fft.Options{Axes: []int{2, 0}, Norm: fft.NormOrtho})
// RFFT2With / IRFFT2With are the 2-D cases.

// Plans take the Norm per call (their length is fixed, so n and axes do not apply):
p.FFTNorm(dst, src, fft.NormOrtho)    // also Plan.IFFTNorm, RealPlan.RFFTNorm/IRFFTNorm,
pn.IFFTNorm(dst, src, fft.NormOrtho)  // PlanN.FFTNorm/IFFTNorm, RealPlan2.RFFTNorm/IRFFTNorm

// Zero frequency to the centre (numpy.fft.fftshift / ifftshift), generic over
// the element type:
c := fft.FFTShift(X)                          // also fft.FFTShift(fft.FFTFreq(n, d))
X = fft.IFFTShift(c)                          // inverse; differs from FFTShift for odd n
C := fft.FFTShiftN(F, shape, nil)             // every axis, or the listed ones
F = fft.IFFTShiftN(C, shape, nil)

// The length to zero-pad to (scipy.fft.next_fast_len):
m := fft.NextFastLen(len(x), false)  // smallest 7-smooth length >= len(x)
mr := fft.NextFastLen(len(r), true)  // smallest EVEN 7-smooth length (real transforms)
```

`NextFastLen` follows this library's engines, not scipy's: lengths
`2^a·3^b·5^c·7^d` run entirely on specialized radix-2/3/4/5/7/8 passes, while a
factor 11 or 13 takes a general O(p²) pass and a larger prime goes to
Rader/Bluestein — several times slower per point. A real transform of odd length
cannot use the half-length packing, so the real rule also requires an even
length.

Where this differs from numpy: an `N` of zero means "numpy's default" rather
than an error, and a transform of zero points returns an empty slice (numpy
raises); an axis listed twice is refused (numpy's `fftn` transforms it twice);
`IRFFTN`/`IRFFTNWith` take the real output's shape instead of numpy's
`s`, and the N-D transforms do not pad or crop axes (numpy's `s` argument).

### Accuracy contract

Bound: relative RMS error <= c·ε·log2(n), c from 0.5 to 2.25 per function family, measured (docs/accuracy.md)

Oracle: double-double, twiddles from math/big at 200 bits; asserted by TestAccuracyBound

Exact: Options.Exact keeps the reference arithmetic, v0.28.16's bits on the same machine

Every transform, in both precisions, with the default arithmetic and with
`Options.FMA`, stays within `c·ε·log2(n)` of the exact result in relative RMS
error, with `ε` 2^-52 (float64) or 2^-23 (float32) and `c` between 0.5 and 2.25
per function family (measured, not proved; the worst ratio seen is 1.03). "Exact" is a double-double
oracle (twiddles from `math/big`) in the test suite; the constants, the lengths
measured and what the check can and cannot see are in
**[docs/accuracy.md](docs/accuracy.md)**.

### Fused multiply-add: the default on amd64 (`Options.FMA`, `NoFMA`, `Exact`)

The default arithmetic fuses multiply-adds on amd64 CPUs with FMA3: twiddle
products and butterfly constants are fused, and on Cascade Lake class CPUs
(AVX-512) 1,024 and 2,048 points take radix-32 passes that only the fused plans
have. The results differ from the unfused arithmetic (v0.31.1 and before) in
the last bits and are as accurate: every transform stays inside the bound of
the accuracy contract above with the fused default (docs/accuracy.md), and
against long-double scipy the error was 0.76–1.08× the unfused one over 90
transforms (Round 41). On arm64 gc already fuses the Go code, and the other
architectures and CPUs without FMA3 compute as before.

So the same machine and route give the same bits, every route stays within the
bound, and the bits are not promised to match across CPUs: different amd64 CPUs
can choose different routes for some lengths (165 of 417 cases measured at
v0.28.16 differ between Zen 3/4/5 and a Xeon), and a CPU with FMA3 now computes
different last bits from one without.

Three options say what you want instead of the default:

```go
X := fft.FFTWith(x, fft.Options{FMA: true})    // the fused plans, explicitly: the default where FMA3 runs
Y := fft.FFTWith(x, fft.Options{NoFMA: true})  // the default without fusing, whatever the CPU
Z := fft.FFTWith(x, fft.Options{Exact: true})  // the reference arithmetic, v0.28.16's bits
p := fft.NewPlanWith(1024, fft.Options{NoFMA: true}) // also NewRealPlanWith, NewPlanNWith, NewRealPlan2With
```

- `FMA` is kept for code written when fusing was opt-in; it changes nothing on
  amd64 with FMA3, and is the default arithmetic elsewhere. `NoFMA` and `FMA`
  together panic.
- `NoFMA` turns the fusing off and keeps the rest of the default: the output
  does not depend on whether the CPU has FMA3.
- `Exact` is the reference arithmetic as compiled by gc (separately rounded
  multiplies and adds in the SIMD kernels; on arm64 gc fuses multiply-adds in
  the Go reference, so amd64 and arm64 differ), in the reference's order of
  operations: v0.28.16's bits on the same machine. The tests pin it to digests
  of v0.28.16's outputs (amd64 and arm64); the tests that hold the transforms to
  the Go reference bit for bit build their plans with it. It excludes `FMA`.

All three are accepted by every `...With` function (the float32 transforms
ignore `FMA` and `NoFMA`) and by `NewPlanWith`, `NewRealPlanWith`,
`NewPlanNWith` and `NewRealPlan2With`, and each arithmetic has its own plan
caches, so a plan of one is never handed out for another.

What fusing gains (in-process against the unfused plan, one core; BENCHMARKS.md,
Rounds 41 and 42, and the Zen 4 and Cascade Lake tables of
[#152](https://github.com/go-fft/fft/pull/152) and the flip pull request):

| | Cascade Lake (AVX-512) | Zen 3 (AVX2) |
|:--|:--|:--|
| complex 1,024 | **1.22×**, 1.19 → 0.94 × FFTW (re-measured 2026-11-07 on a slower day: 1.24 → 1.03) | 1.00–1.04×, 1.13 → 1.10 × FFTW |
| complex 2,048 / RFFT 4,096 | 1.11× / 1.09× | 1.03× / 1.03× |
| complex 256, 512 | 1.07–1.08× | 1.06× |
| composites (1,000 … 1,920), 2-D | 1.01–1.05× | 1.01–1.05× |
| rows it does not speed up | 4,096–16,384 (fusing off there: the unfused kernels) | most rows ±2% |

On those two CPUs the plan fuses only the passes measured faster fused, so no
row measured slower than the unfused plan beyond noise (lowest 0.99); on a Zen 4
the 142 refbench rows are 0.92 to 1.00 of the unfused time. Elsewhere on amd64
(Haswell, Zen 2/4) every pass fuses.

`Exact` does not cover the DCT, DST and MDCT plans, which take no `Options`.
Their twiddle passes, and the MDCT's fold and unfold from 256 samples up, are
[go-simd/floats](https://github.com/go-simd/floats)
kernels that fuse multiply-adds (NEON on arm64, AVX2+FMA on amd64) and the
portable loops elsewhere, so their bits differ from v0.30.0's and between a CPU
with and without FMA; they are held to the accuracy bound and to digests of this
arithmetic, not to the reference's bits. An `Exact` mode for them is a step 3
item of [#121](https://github.com/go-fft/fft/issues/121).

### DCT and DST (scipy.fft.dct / dst)

The discrete cosine and sine transforms of types I–IV, forward and inverse,
with scipy's definitions and its `norm` argument (`fft.NormBackward`, the
default, `fft.NormOrtho` and `fft.NormForward`):

```go
y := fft.DCT(x, 2, fft.NormOrtho)      // scipy.fft.dct(x, type=2, norm="ortho")
x2 := fft.IDCT(y, 2, fft.NormOrtho)    // scipy.fft.idct: IDCT(DCT(x)) == x for every norm
s := fft.DST(x, 1, fft.NormBackward)   // scipy.fft.dst(x, type=1)
x3 := fft.IDST(s, 1, fft.NormBackward) // scipy.fft.idst

// N-D over a row-major shape, every axis (scipy.fft.dctn / idctn / dstn / idstn):
Y := fft.DCTN(img, []int{rows, cols}, 2, fft.NormOrtho)

// Reusable plans, writing into your slice (dst may alias src):
dp := fft.NewDCTPlan(n, 2)             // also NewDSTPlan(n, typ)
dp.DCT(dst, src, fft.NormOrtho)
dp.IDCT(dst, src, fft.NormOrtho)

// The MDCT of the audio codecs (AAC, Vorbis, Opus CELT): a block of n samples
// (n even) to n/2 coefficients and back, float64 or float32 (NewMDCTPlan32),
// 0 allocations, checked against the O(n^2) definition in double-double. With a
// Princen-Bradley window (SineWindow, KBDWindow) on both sides, blocks advancing
// by n/2 and an inverse scale of 2/(n/2) the overlap-add reconstructs the input.
mp := fft.NewMDCTPlan(n)
mp.MDCT(coef, samples, 1)            // len(coef) >= n/2, len(samples) >= n
mp.IMDCT(out, coef, 4/float64(n))    // len(out) >= n

// float32 data with float64 arithmetic, rounded once on output: no conversion
// passes, and a float32 rounding of error instead of the float32 plans'
// log2(n) stages (docs/accuracy.md). Also dp.DCTMixed / IDCTMixed for a DCT-IV plan.
mp.MDCTMixed(coef32, samples32, 1)
mp.IMDCTMixed(out32, coef32, 4/float64(n))

// Two independent DCT-IV(64) per call (HE-AAC's QMF runs six per slot): on arm64
// one NEON kernel with a transform in each lane, 33% faster than two calls
// (Apple M4 Max: 90 -> 60.6 ns float64, 107 -> 71.3 ns Mixed; a single DCT-IV(64)
// call is 88 -> 43.7 ns). The same kernels exist for DCT-IV(128), the AAC short
// block's MDCT of 256 samples, and the MDCT/IMDCT of 128 samples (also their Mixed
// forms) run on the kernel of 64 on arm64. On amd64 with AVX2 and FMA3 one AVX2
// kernel of 64 holds a complex value of both transforms in each 256-bit register:
// on a Ryzen 9 7950X (Zen 4) a pair of float64 is 122.5 -> 58.5 ns and a pair of
// Mixed 122.5 -> 68.3 ns, and a single call is unchanged (60 ns). Elsewhere, and
// for other lengths, the pair form is two calls.
// DCTPair, IDCTPair, DCTMixedPair, IDCTMixedPair; the results are within the
// same error bound as DCT, not bit for bit.
dp := fft.NewDCTPlan(64, 4)
dp.DCTPair(dst0, dst1, src0, src1, fft.NormOrtho)
dp.DCTMixedPair(dst32a, dst32b, src32a, src32b, fft.NormOrtho)

// The same in single precision throughout (no widening to float64): DCTPlan32
// DCTPair, IDCTPair, DCTQuad and IDCTQuad. On amd64 with AVX2 and FMA3 a
// DCT-IV(64) runs a float32 kernel with one complex value of every stream in each
// register; on a Ryzen 9 7950X a pair is 70.7 ns through DCTMixedPair and 57.5 ns
// here, and a quad (four transforms) 97 ns, 48.6 ns per pair. Elsewhere the forms
// are the single calls. Within eps32*log2(n) of the double-double oracle.
sp := fft.NewDCTPlan32(64, 4)
sp.DCTPair(d0, d1, s0, s1, fft.NormOrtho)
sp.DCTQuad([4][]float32{d0, d1, d2, d3}, [4][]float32{s0, s1, s2, s3}, fft.NormOrtho)
```

`NormOrtho` applies scipy's default orthogonalisation (`orthogonalize=True`),
which makes every type an orthonormal matrix; the inverse of type 2 is type 3
and vice versa, types 1 and 4 are their own inverses. Every length is
supported except those scipy rejects: DCT-I needs at least 2 points, the
others 1. Each transform is O(N log N) on the package's real and complex FFTs:
Makhoul's algorithm (one N-point real FFT) for DCT-II/III, a half-length
complex FFT for even-length DCT-IV, a symmetric extension for DCT-I and DST-I,
and index identities for the DSTs. The results are checked against scipy's
own values (`testdata/scipy_r2r.json`).

DCT-II and DCT-III of 32, 64 and 128 points run a fused route (`dct23.go`): the
reorder is written into the half-length FFT's input and one
`floats.MirrorCombine` / `MirrorCombineSplit` pass (AVX2+FMA on amd64) untangles
and twiddles at once. On a Ryzen 9 7950X, one pinned core, against FFTW 3.3.10
AVX-512 `REDFT10` / `REDFT01` (fresh processes, alternating order): DCT-II at 64
points 1.25x FFTW before, 1.03x after; DCT-III 1.40x before, 1.15x after (the
inverse's input is gathered by `floats.CMulZipRev`, also AVX2+FMA). The results are within
`2·ε·log2 n` of a double-double oracle (`dct23_test.go`), not bit for bit with
the generic route.

At 32 and 64 points on Zen 4 (other CPUs keep the route above) the whole
transform is one generated straight-line kernel (`internal/gendct23`, assembly in
`internal/kernels/dct23_amd64.s`: reorder, split-radix FFT, untangle and twiddle with
every constant folded in, 32 vector registers, FMA). Same machine and method,
ns per call: DCT-II 32 points 57.0 -> 30.6 (FFTW 41.9, 0.73x), 64 points
84.1 -> 68.7 (FFTW 81.3, 0.85x); DCT-III 32 points 69.3 -> 39.8 (FFTW 43.5,
0.91x), 64 points 98.0 -> 90.0 (FFTW 84.3, 1.07x). 128 points keeps the route above.

Since v0.45.1 (bit-identical) the generator schedules the kernels with a
register-pressure list scheduler: spills fall from 182 to 104 in `Dct3x64` (frame
1,456 to 832 bytes), 98 to 70 in `Dct2x64`, 23 to 7 in `Dct3x32` and 7 to 2 in
`Dct2x32`; the DCT-III kernel at 64 points, called directly, takes 77.2 -> 62.0 ns
on Zen 4, about 0.91x FFTW's time (it was 1.07x). A SHA-256 test pins the kernel
bits.

Since v0.46.0 Bluestein's pointwise complex multiply on the default (FMA) path
calls `floats.CMulTo` of go-simd/floats v0.32.0; the package's own multiply
kernels are gone. `Options{Exact: true}` and `Options{NoFMA: true}` keep the Go
loop (Exact is still bit-identical to v0.28.16). The default-path Bluestein bits
change on Zen 4 and other FMA CPUs, within the bound: the worst Bluestein error
ratio is 0.674 (complex n=23, it was 0.598) and the worst of the family 0.718,
under the 0.74 bound. Whole Bluestein transform: -8 to -30% on Cascade Lake, which
ran the scalar loop before; +1 to 2% on Zen 4 and Neoverse N1, whose small-n part
is recovered in v0.47.0 (below).

Since v0.47.0 (a MINOR release: the default-path Bluestein bits change on amd64,
arm64 stays bit-identical, Exact and NoFMA are unchanged) go-fft requires
go-simd/floats v0.36.0, whose `CMulTo` finishes its own tail
(go-simd/floats#83, which fixes go-simd/floats#81 and go-simd/floats#82). Whole
Bluestein against v0.46.0 (benchstat, p < 0.01): small n is faster on all three
hosts, Zen 4 n=47 -2.7%, Cascade Lake n=47 -5.5% and n=94 -3.9%, Neoverse N1 n=47
-5.0%, n=94 -5.2% and n=10007 -2.5%; large n on amd64 shows no measurable change.
Accuracy is unchanged (complex Bluestein worst 0.674, family worst 0.718, under the
0.74 bound).

Exception to "the default equals Exact where it does not fuse": on s390x and
ppc64le the default Bluestein product runs `floats.CMulTo` (VX and VSX kernels,
go-simd/floats v0.39.0), whose contract is an error bound, not the Go loop's bits,
so the default's Bluestein bits differ there from `Exact` and `NoFMA`, which keep
the loop; arm64's NEON kernel gives the loop's bits (asserted bounds: 1.5 for c2c,
2.0 for r2c).

### Single precision (complex64 / float32)

As `scipy.fft` does for `complex64` input, the 1-D transforms also run in single
precision, complex64 in and complex64 out, for any length:

```go
X := fft.FFT32(x)             // []complex64 → []complex64, unnormalized
y := fft.IFFT32(X)            // normalized by N
R := fft.RFFT32(r)            // []float32 → N/2+1 bins of []complex64
z := fft.IRFFT32(R, len(r))   // back to []float32

p := fft.NewPlan32(n)                  // reusable, safe for concurrent use
p.FFT(dst, src)                        // also p.IFFT
p.FFTNorm(dst, src, fft.NormOrtho)     // numpy/scipy norm=: NormBackward (default),
p.IFFTNorm(dst, src, fft.NormOrtho)    // NormOrtho, NormForward
rp := fft.NewRealPlan32(n)
rp.RFFT(dst, src)                      // also rp.IRFFT, rp.RFFTNorm, rp.IRFFTNorm
```

The multi-dimensional transforms, the numpy optional arguments and the DCT/DST
have single-precision forms too, so the float32 surface mirrors the float64 one:

```go
// N-D and 2-D (scipy.fft.fftn/ifftn/fft2/ifft2/rfftn/irfftn/rfft2/irfft2):
F := fft.FFTN32(data, shape)              // []complex64, row-major
d := fft.IFFTN32(F, shape)                // normalized by the product of the shape
F2 := fft.FFT2_32(img, [2]int{rows, cols}) // also IFFT2_32
S := fft.RFFTN32(vol, shape)              // []float32 → last axis keeps n/2+1 bins
v := fft.IRFFTN32(S, shape)               // the REAL output's shape
R2 := fft.RFFT2_32(img, [2]int{rows, cols}) // also IRFFT2_32

pn := fft.NewPlanN32(rows, cols)          // FFT, IFFT, FFTNorm, IFFTNorm
r2 := fft.NewRealPlan2_32(rows, cols)     // RFFT, IRFFT, RFFTNorm, IRFFTNorm

// numpy's n, norm and axes, with the same fft.Options:
X := fft.FFT32With(x, fft.Options{N: 1024, Norm: fft.NormOrtho}) // also IFFT32With
R := fft.RFFT32With(r, fft.Options{N: 1024})                     // also IRFFT32With
h := fft.HFFT32(half, n)                                         // HFFT32With, IHFFT32, IHFFT32With
B := fft.RFFTN32With(rows, []int{m, n}, fft.Options{Axes: []int{-1}}) // batched rows
// FFTN32With, IFFTN32With, FFT2_32With, IFFT2_32With, IRFFTN32With,
// RFFT2_32With, IRFFT2_32With likewise.

// DCT/DST types I–IV (scipy.fft.dct/idct/dst/idst/dctn/idctn/dstn/idstn):
y := fft.DCT32(x32, 2, fft.NormOrtho)     // also IDCT32, DST32, IDST32
Y := fft.DCTN32(img32, shape, 2, fft.NormOrtho) // also IDCTN32, DSTN32, IDSTN32
dp := fft.NewDCTPlan32(n, 2)              // dp.DCT/dp.IDCT; NewDSTPlan32 likewise
```

Each name is the float64 one with `32` appended; where that name already ends
in a digit an underscore keeps the two numbers apart (`FFT2_32`, not `FFT232`),
as the standard library's `crypto/sha512.Sum512_256` does.

The precision follows `scipy.fft`, which keeps float32 and complex64 (as
`numpy.fft` does since NumPy 2.0). The arithmetic is float32; twiddles, the
Rader/Bluestein kernels and the DCT/DST twiddles are computed in float64 and
rounded once, and a `Norm` factor is rounded once and applied in one pass. The
error is within `eps32·log2(N)` of the exact transform, relative to the
vector's 2-norm (`eps32 = 2⁻²³`; N is the number of points combined: the
product of the transformed axes, or the DCT/DST's logical size), on every
length and shape tested, and the results agree with scipy's own float32 ones
(`testdata/scipy_f32.json`). On amd64 with AVX2 and on arm64, the float32
Stockham passes of radix 2, 3, 4, 5 and 8 run on SIMD kernels, four complex64
per register, bit-identical to the Go passes (BENCHMARKS.md, Round 22).

One exception, on an AMD Zen 4 and an Intel Cascade Lake (CPUID family 6, model
0x55, stepping 5, 6 or 7; measured at stepping 5) with AVX-512: a `Plan32` of
64, 128, 256, 512, 1,024, 2,048, 4,096 or 8,192 points (and so the
`RealPlan32` of twice those lengths) runs one generated AVX-512 kernel, two
fused passes with eight complex64 per register and the twiddles between them
folded into the first (`internal/genfused256`; the complex128 kernels of the
fused plans, in single precision). Their float32 twiddles are the 400-bit value
rounded once. It is not bit-identical to the passes; its error is asserted
against a double-double oracle at `eps32·log2(N)` times the c2c constant, and
`Options.Exact`, `Options.NoFMA`, the plans under the N-D, 2-D real, DCT, DST and
MDCT transforms (golden digests pin their bits) never take it. Ryzen 9 7950X, one
core, fresh process per row, FFTW 3.3.10 AVX-512 single precision, ns per
transform (go-fft before, now, FFTW): 64 40.1, 22.9, 22.2; 256 128.4, 79.5,
77.0; 1,024 563.1, 367.6, 380.3; 4,096 4,578, 2,170, 2,277; 8,192 8,568,
5,221, 7,221. On a Cascade Lake it takes 0.43
to 0.66 of the passes' time (FFTW single precision not measured there). The call
into the kernel is inlined per length (`Plan32.FFT` goes straight to `execute`,
which calls one small function per kernel length, instead of one function with a
switch over the lengths): against FFTW the ratios are 64 1.01 to 1.04, 128 1.02,
256 0.98 to 1.01 and 2,048 0.94 to 0.99, so no length from 64 to 8,192 is above
1.05. The 2,048-point kernel is 32×64 (a 32-point first pass, a 64-point second
pass), 8% faster than 64×32 on a Zen 4 and 11% on a Cascade Lake. See
docs/perf-history.md.

## Performance

**How a length is transformed.**
- **Lengths whose prime factors are all ≤ 13** go through an iterative
  mixed-radix **Stockham** engine: radix-8/4/2/3/5/7 straight-line passes plus a
  general radix-p pass for 11 and 13.
- **A prime whose N−1 is 7-smooth** uses **Rader's algorithm**; **every other
  length** uses **Bluestein's chirp-z**. Both convolve on the Stockham engine.
- **Powers of two on loong64, s390x and amd64 without AVX2, and above 65536 on
  riscv64,** take an iterative, cache-blocked **radix-4 kernel** instead (SSE2
  butterflies on amd64).
- **Real transforms** run a half-length complex transform and one untangle pass.
- **N-D transforms** run the 1-D transform along each axis, spread across cores
  above a work threshold. On amd64 with AVX2, an axis other than the last runs
  as batched passes over strips of 16 or 32 neighbouring lines, read and
  written where they lie in the array, instead of gathering each line.

Twiddle factors are computed once per length and cached.

**SIMD.** On amd64 the Stockham passes run as generated **AVX2** kernels, and
powers of two of 256 points or more as **AVX-512** kernels where the CPU and
the OS allow it (AVX-512F **and** AVX-512DQ, with the OS saving ZMM and opmask
state; a CPU with F but no DQ, such as Knights Landing, takes the AVX2 kernels;
an AMD Zen 4 runs the AVX2 kernels up to 65,536 points, where
hardware counters showed them 5–27% faster, except 2,048, and 65,536 to 262,144
with the 512-bit split layout, 3–6% faster still); the real-FFT untangle has an AVX2
kernel too. They keep the
Go code's arithmetic order (separately rounded multiplies and adds, no FMA), so
their results are **bit-identical** to the Go passes, and the tests compare
them bit for bit on generic, ±0 and ∞ inputs. These are the kernels of
`Options.NoFMA` and `Exact`; the default plans on amd64 with FMA3 run fused
twins of them (`Options.FMA`, above), each bit-identical to a Go reference
written with `math.FMA`. One exception, on an AMD Zen 4 (and, for 256 and 2,048
points only, an Intel Cascade Lake: CPUID family 6, model 0x55, stepping 5, 6 or
7, measured at stepping 5, 0.82 and 0.79 of the passes' time there, against FFTW 3.3.10 with AVX-512
at 1.00 and 1.11 before, 0.82 and 0.87 after; see docs/perf-history.md): a default or FMA
plan of **256 points** runs a single generated AVX-512 kernel (two fused 16×16
passes, each 16-point DFT held in zmm registers, the twiddles between the passes
folded into the first; `internal/genfused256`). It is not bit-identical to the
passes; its error is asserted against a double-double oracle at the c2c bound,
and `Exact` and `NoFMA` plans never take it. Ryzen 9 7950X, one core, 21
interleaved rounds, complex128 forward, against FFTW 3.3.10 with AVX-512:
155.4 ns before (1.15×), 143.7 ns now (1.07×; FFTW 134.8 ns); the rows of a 256×256 `PlanN` take it too: 153.8 µs before, 145.1 µs now (FFTW 146.5 µs). **1,024 points** takes the same route with two fused 32×32 passes (a loop of eight iterations over one generated body per pass; the 32 values of a 32-point DFT fill the 32 zmm registers, so the generator spills): 886 ns before (1.18×), 816 ns now (1.09×; FFTW 750 ns), forward, same method. **2,048 points** takes it as well (32×64: a 32-point first pass, a 64-point second pass that spills): 2,272 ns before (1.22×), 1,875 ns now (1.00×; FFTW 1,869 ns), and the real transform of 4,096 points, whose half plan is that one, goes from 2,789 ns (1.12×) to 2,502 ns (1.00×; FFTW 2,493 ns). On **arm64** the radix-2/3/4/5/8
passes, and the radix-2 to 5 final passes over an even number of blocks, run as
generated **NEON** kernels. gc fuses multiply-adds on arm64, so each kernel
reproduces, pass by pass, which product the Go code rounds and which it fuses;
the results equal the Go code's bit for bit, except the bits of a NaN produced
from infinite inputs, which IEEE 754 leaves unspecified (on amd64 too, where a
kernel may add two NaNs in the other order and propagate the other one). On riscv64, loong64,
ppc64le and s390x the passes are Go code, compiled to scalar instructions (gc
does not vectorize; it fuses multiply-adds on all of them). Complex-multiply
kernels for riscv64 (RVV) and s390x exist and are validated bit-identical, but
are not used: the scalar loop measured as fast.

## Why not cgo / FFTW?

FFTW3 is a C library: binding it reintroduces a C toolchain, cross-compilation
pain, and a non-Go build. A pure-Go implementation cross-compiles to every Go
target for free and is `CGO_ENABLED=0` clean — which is what makes it usable as
the FFT backend for an embedded Ruby (`go-embedded-ruby`) and for the wider
go-* ecosystem.
